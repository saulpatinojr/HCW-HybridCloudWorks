# Cosmos restore — the drill that proves RPO 24 h / RTO 8 h

> **Status: exporter armed and running since 2026-09-09; no drill run yet.**
> The exporter (`cosmosExportScheduler` and the `cosmos-export-container`
> job, `functions/src/lib/backup/`) runs while `FEATURE_FLAG_COSMOS_EXPORT`
> is `true`, which Terraform writes from the `cosmos_export_enabled`
> workspace variable; its first run completed 2026-09-09 03:00 UTC and the
> daily missing-run alert is live. The first drill was declined on 2026-09-09
> and approved on 2026-10-06 (estate review, finding PLAT-1): it is due, and
> the Drills table at the end is empty until it has run. This page records
> what was **restored** and how long it took, not what was configured.

The design is [ADR 0028](../decisions/0028-cosmos-out-of-account-export.md):
every Sunday the Function App exports every included container in full, every
other day it exports each container's change feed since the previous run, and
the copies land as gzip NDJSON in the `cosmos-export` blob container on
`stsiteprodcus01` — a different Azure resource, in a different resource group,
geo-replicated to the paired region. A restore is "the latest complete full
plus every complete delta after it", upserted into a fresh account.

The objectives (owner decision 2026-08-30, #231): **RPO 24 hours** — the
newest complete run is at most a day old — and **RTO 8 hours** — from the
decision to restore to the site's public reads answering from the restored
account. The drill below measures both. Run it once a quarter.

## What comes back, and what does not

Say this before the drill, so nothing in it is a surprise:

- **61 of the 74 containers**: the 44 authored and 10 configuration containers
  from every run, the 7 operational-record containers (`admin_audit_logs`,
  `audits`, `ai_usage`, `telegram_bot_activity`, `workflow_alerts`,
  `workflow_digests`, `content_stats_markers`) as of the last full only. The
  list is code: `functions/src/lib/backup/export-classification.js`.
- **Not restored, by design**: `_snapshots`, `homepage_feeds`, `rss_cache`,
  `tool_service_cache` and `tool_price_history` (regenerated by a publish or a
  scheduled job; the price history restarts from empty, which the owner
  accepted over exporting it),
  `azure_landing_content` and `tool_service_catalog` (re-seeded by a script),
  and the six TTL-bounded job and quota containers. A restored site republishes
  its snapshots and refills its caches on the first scheduled runs.
- **Up to a week of resurrected deletes.** The change feed does not carry
  deletes; only the weekly full reconciles them. A document deleted on a
  Tuesday and restored from Sunday's full plus Monday-to-Saturday's deltas is
  back. Accepted in ADR 0028; the all-versions-and-deletes change feed is the
  revisit path if it ever matters.
- **Document bodies are exact; system fields are not.** `_rid`, `_self`,
  `_etag`, `_attachments` and `_ts` are stripped on restore and re-minted by
  the target account. Nothing in the application reads them across restarts.
- **Continuation state (`state/`) is not restored.** It belongs to the source
  account's change feed and means nothing to another account.

## Is the export running? Read this first

Success is silent and only absence pages (ADR 0028 §5). To see the runs
directly, query Application Insights from PowerShell (the `application-insights`
CLI extension installs itself on first use; the resource is
`appi-site-prod-cus-01`, instance suffix included):

```powershell
az monitor app-insights query --app appi-site-prod-cus-01 -g rg-web-site-prod-cus --offset 14d --analytics-query 'customEvents | where name == "cosmosExportCompleted" | project timestamp, mode = tostring(customDimensions.mode), runId = tostring(customDimensions.runId), containers = toint(customDimensions.containers), docs = tolong(customDimensions.docs), bytes = tolong(customDimensions.bytes), durationMs = tolong(customDimensions.durationMs) | order by timestamp desc' -o table
```

A healthy fortnight shows two `full` rows with `containers` 61 and twelve
`delta` rows with `containers` 54, one per UTC date. A gap in `runId` is a run
that never wrote its manifest — a container job failed or timed out — and the
missing-run alert will have fired on it. An empty table when the exporter has
been armed for more than two days is the same finding as the alert. The
per-container detail is in `traces`:

```powershell
az monitor app-insights query --app appi-site-prod-cus-01 -g rg-web-site-prod-cus --offset 2d --analytics-query 'traces | where message startswith "[cosmosExport]" | project timestamp, message | order by timestamp desc | take 100' -o table
```

Every line names a container, a count and a duration. None names a document.

checkout before believing any error that names it:

### 1. Open the export to the workstation

`stsiteprodcus01` is `Deny` by default at the network and reads are
role-gated at the data plane, so a workstation needs both a firewall rule and
a data-plane role, scoped to the one container. Both are removed in step 6,
and Terraform's next apply on `hcw-azure` would remove the rule anyway (it is
not declared).

```powershell
$ip = Invoke-RestMethod https://api.ipify.org
```

```powershell
az storage account network-rule add -g rg-stor-site-prod-cus --account-name stsiteprodcus01 --ip-address $ip -o none
```

```powershell
$me = (az ad signed-in-user show -o json | ConvertFrom-Json).id
```

```powershell
$storageId = (az storage account show -n stsiteprodcus01 -g rg-stor-site-prod-cus -o json | ConvertFrom-Json).id
```

```powershell
az role assignment create --assignee-object-id $me --assignee-principal-type User --role "Storage Blob Data Reader" --scope "$storageId/blobServices/default/containers/cosmos-export" -o none
```

Success is four silent exits. The role takes up to five minutes to propagate;
if step 2 answers `AuthorizationPermissionMismatch`, wait and rerun step 2 —
that error is propagation, not a wrong command.

### 2. Dry run: what would be restored, and how old is it

```powershell
node scripts/restore-cosmos-export.mjs --storage-account stsiteprodcus01 --dry-run
```

Success looks like:

```text
DRY RUN — counting full/2026-09-13 + 3 delta(s) (2026-09-14 … 2026-09-16) — 60 container(s)
container                         full        deltas      created     replaced                ms
admin_audit_logs                  412         0                                               310
…
Would restore 70112 document(s) across 60 container(s) in 41207 ms (0.7 min) — distinct and overwritten counts come from the upsert responses and are computed only on a real run
```

Read two things off it. **RPO**: the newest run id on the first line is the
recovery point; it must be yesterday's date or today's. **Completeness**: a
`Skipped incomplete runs` line names runs that never wrote a manifest; they are
not applied, and the newest *applied* run is the real recovery point. Writes
nothing, needs no Cosmos account, and is the step to run on its own any time
the question is "what would a restore give me right now".

`no complete full export` means no Sunday run has completed since the exporter
was armed: there is nothing to restore yet, and the drill stops here.

### 3. Create the target account

A fresh serverless account in its own resource group, tagged with the day it
must be gone by — the 2026-08-24 sandbox stayed for weeks because its expiry
lived somewhere other than the resource (`infra/scratch.tf` keeps that record).
Account keys are never read; the drill authenticates the same way production
does, so a restore that passes proves the RBAC path too.

```powershell
$expires = (Get-Date).AddDays(2).ToString('yyyy-MM-dd')
```

```powershell
az group create -n rg-db-site-sbx-cus -l centralus --tags purpose=cosmos-restore-drill expires=$expires -o none
```

```powershell
az cosmosdb create -n cosmos-site-sbx-cus -g rg-db-site-sbx-cus --locations regionName=centralus --capabilities EnableServerless --default-consistency-level Session -o none
```

The account takes five to ten minutes. Then the database and every container
from the provisioned spec, with the partition key each one has in production
— the five containers not keyed on `/id` restore wrongly into `/id`
containers, silently:

```powershell
az cosmosdb sql database create -a cosmos-site-sbx-cus -g rg-db-site-sbx-cus -n hcw -o none
```

```powershell
$spec = Get-Content infra/cosmos-containers.json -Raw | ConvertFrom-Json; foreach ($c in $spec.containers) { az cosmosdb sql container create -a cosmos-site-sbx-cus -g rg-db-site-sbx-cus -d hcw -n $c.name --partition-key-path $c.partition_key_path -o none }
```

```powershell
az cosmosdb sql container list -a cosmos-site-sbx-cus -g rg-db-site-sbx-cus -d hcw -o json | ConvertFrom-Json | Measure-Object | Select-Object Count
```

Success is a `Count` equal to the number of containers in the spec, which
`$spec.containers.Count` prints (75 on 2026-10-12). Creating them one at a time
takes about a minute each, and Azure prints each one's state (`Enqueued`,
`Dequeued`, `Succeeded`) as it goes: the repeating pattern is the loop moving
through the list, not a loop stuck on one container. Grant the signed-in user the built-in
data-plane contributor role on the new account (the role id is the same
constant in every tenant):

```powershell
az cosmosdb sql role assignment create -a cosmos-site-sbx-cus -g rg-db-site-sbx-cus --role-definition-id 00000000-0000-0000-0000-000000000002 --principal-id $me --scope "/" -o none
```

### 4. Restore and verify

```powershell
node scripts/restore-cosmos-export.mjs --storage-account stsiteprodcus01 --target-endpoint https://cosmos-site-sbx-cus.documents.azure.com:443/ --verify
```

Success looks like the dry run with `created` and `replaced` filled in. The
upsert answers 201 for a document the target had not seen and 200 for one an
earlier layer, or an earlier attempt, already wrote. The `target` column on
every row equals what the container held before the run plus what the run
created: into a fresh account that is `created`, and an empty container
reads `0`. An operational container such as `admin_audit_logs` shows `0`
under `deltas`, because it is in the weekly full and in no delta, by design.
The last line reads
`Restored 11971 document(s): 11937 created, 34 replaced (already in the target, or superseded by a later layer), across 62 container(s) in 104979 ms (1.7 min)`,
with exit code 0. A row ending `MISMATCH` is a container whose count in the
target is not that; it names the count it expected, the script exits 1, and
the drill has not passed until the cause is known. The cost of this step is about
$3 in write request units (cost analysis, #385).

### 5. Spot-check the site's public reads against the restored account

Counts prove the copy landed; a read proves the site can serve from it. Run
the Function App locally against the target account — the local host
authenticates with the same `az login` identity, and needs Azure Functions
Core Tools (`func`) on the path — and ask it the two anonymous questions a
visitor asks first. The settings file is gitignored; this writes the four
values the public reads need and nothing else (no key, no connection string):

```powershell
@{ IsEncrypted = $false; Values = @{ FUNCTIONS_WORKER_RUNTIME = 'node'; AzureWebJobsStorage = 'UseDevelopmentStorage=true'; COSMOS_ENDPOINT = 'https://cosmos-site-sbx-cus.documents.azure.com:443/'; COSMOS_DATABASE = 'hcw' } } | ConvertTo-Json | Set-Content functions/local.settings.json
```

```powershell
npm --prefix functions start
```

The host logs an error per timer listener because no storage emulator is
running; that is expected, every timer is off without its flag, and the HTTP
routes serve regardless. In a second PowerShell window:

```powershell
(Invoke-RestMethod http://localhost:7071/api/public/content).items | Measure-Object | Select-Object Count
```

```powershell
Invoke-RestMethod http://localhost:7071/api/public/podcasts | ConvertTo-Json -Depth 3 | Select-Object -First 30
```

Success is a non-zero `Count` and a podcast list with titles in it. Stop the
local host with Ctrl+C when done. This is the point the RTO is measured to:

```powershell
$elapsed = (Get-Date) - $drillStart; $elapsed.ToString()
```

Under `08:00:00` meets the objective. Record the elapsed time, the run ids and
the document count in the Drills table below **before** tearing down.

### 6. Tear down

The target holds a full copy of production data; it does not outlive the
drill. The resource-group delete is asynchronous and irreversible.

```powershell
az group delete -n rg-db-site-sbx-cus --yes --no-wait -o none
```

```powershell
az storage account network-rule remove -g rg-stor-site-prod-cus --account-name stsiteprodcus01 --ip-address $ip -o none
```

```powershell
az role assignment delete --assignee $me --role "Storage Blob Data Reader" --scope "$storageId/blobServices/default/containers/cosmos-export" -o none
```

The local settings file points at the account just deleted; remove it:

```powershell
Remove-Item functions/local.settings.json
```

```powershell
az group exists -n rg-db-site-sbx-cus
```

`false` (after a few minutes) is the end of the drill.

## A real restore, not a drill

The same steps with two differences. The target is a permanent account whose
name, resource group and firewall the owner decides at the time (the scratch
names above are for something that gets deleted); and after step 4 the Function
App's `COSMOS_ENDPOINT` app setting (Terraform, `infra/functionapp.tf`) and the
identity's data-plane role assignment (`infra/cosmos.tf`) move to the new
account. Then republish snapshots and let the ingest timers refill the caches.
The restore script refuses a target whose account name has `-prod-` in it,
because a restore writes backup copies over whatever the target holds; a real
restore into a new production-named account adds `--allow-production-target`.
The live account is never the target.
Deleted-in-the-last-week documents must be re-deleted by hand from the admin
portal; the audit rows say which.

## A regional loss

Nothing on this page rehearses one, and the objectives above do not cover
one: continuous backup restores into the same region, and the drill restores
into a scratch account in the same region. This section says what exists and
the order it would be used in, so the first regional incident starts from a
list rather than a blank page. It is untested, and the honest estimate is that
it does not fit inside the 8-hour RTO.

What survives a regional loss:

- The exports. `stsiteprodcus01` is RA-GRS, so the `cosmos-export` container
  is readable from the paired region at once (the secondary endpoint) and
  writable after an account failover.
- The code and the configuration: this repository, HCP Terraform state, and
  every Key Vault *reference* in `infra/`.
- The owner's copies of the secret values (the password manager; Key Vault
  itself is single-region and its backups restore only into the same
  geography).

What does not: the Cosmos account and its continuous backup, the Function
App, the Key Vault, Log Analytics, and the Static Web App's deployment.

The order:

1. **Decide.** A regional outage that Azure expects to resolve in hours is
   waited out; the site's public pages stay up from the edge (ADR 0011). A
   restore elsewhere is for a loss Azure is not going to reverse.
2. **Storage.** Initiate the account failover for `stsiteprodcus01` so the
   exports and media become primary in the paired region. Read the export
   manifest from the secondary endpoint first; the failover takes time and
   the dry run (§2 above) needs only reads.
3. **Compute and data, in a new region.** `infra/` names every resource with
   `region_abbreviation` (default `cus`), so a second region is a second set
   of names, not a rename: set the region variables in the workspace, apply,
   and treat the result as a fresh estate. The Cosmos account it creates is
   the restore target: steps 3 and 4 of the drill, into that account, from
   the exports.
4. **Secrets.** Re-seed every Key Vault value from the owner's copies through
   the API Keys page or the seeding window; the required-inputs standard
   lists each name. The origin secret must change in its three places together.
5. **Edge.** Repoint the Cloudflare records for the API and the site at the
   new hostnames; the Static Web App is redeployed by the frontend workflow.
6. **Verify** with §5 above (public reads against the restored account) and
   `scripts/smoke-deployed.mjs`.

Record what it took in the Drills table with the note `regional`, even when it
was real rather than rehearsed.

## Drills

One row per drill, real restores and regional ones included. Add the row
before tearing down (step 5 says when), in this shape:

```text
| 2026-10-20 | 03:12:45 | 21 h | saulpatinojr | full/2026-10-19 + 1 delta | 70112 | first drill |
```

| Column | What goes in it |
| --- | --- |
| Date | The day the drill ran, UTC, as `YYYY-MM-DD`. Nothing else in this cell: the check below reads it |
| RTO measured | `$elapsed` from step 5, `hh:mm:ss`. The objective is under `08:00:00` |
| RPO measured | Hours between the newest applied run in step 2 and `$drillStart`. The objective is under 24 h |
| Who | Who ran it |
| Applied runs | The full and the deltas step 4 applied, as step 2 names them |
| Documents | The count step 4 reports |
| Notes | `regional` for a regional restore; anything that went wrong |

A row whose Date is `—` is a placeholder, not a drill. Every Monday,
[`check-drill-age.yml`](https://github.com/saulpatinojr/HCW-HybridCloudWorks/actions/workflows/check-drill-age.yml)
runs `scripts/check-drill-age.mjs` over this table and fails, opening an
issue or commenting on the open one, when the newest dated row is more than
100 days old or there is none: a quarter plus ten days' grace. A Date cell it
cannot read as a real, past calendar date fails the check too, so a typo
cannot pass as a drill, and so does a dated row with any cell but Notes left
empty or `—`: a date alone is not evidence of a drill. Keep the columns
exactly as headed below; the check reads them by name. Run it locally the
same way:

```powershell
node scripts/check-drill-age.mjs
```

Exit 0 and `Last drill: <date>, <n> day(s) ago` is a current drill; exit 1
names how old the last one is, or says there is none; exit 2 means the table
could not be read and quotes the line.
